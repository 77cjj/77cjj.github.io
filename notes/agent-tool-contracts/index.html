工具与上下文 / 原文解读

工具描述，不是给开发者看的装饰文字.

Agent 能否选对工具，取决于接口是否讲清用途和边界。

Dream · 2026.09短篇阅读札记
参考原文Anthropic · Writing effective tools for agents ↗以下是独立中文札记，并非原文翻译。来源观点与个人推论分开展示。

问题从哪里来

同一套能力，可以被包装成许多名字相似、返回大量原始数据的工具，也可以是一组目的明确、结果精简的动作。Anthropic 的工程文章把工具视为确定性软件与非确定性 Agent 之间的契约。

原文给出的线索

  1. 工具名与说明需要区分“什么时候用”和“什么时候不该用”，而不只是重复函数签名。
  2. 返回内容应帮模型完成下一步判断：稳定的字段、必要的上下文、明确的错误，比一大段噪声更有用。
  3. 把真实任务放进测试集，检查 Agent 是否选对工具、传对参数，并在失败时正确恢复。

我的理解 · 可以怎么试

我的实现原则是给每个工具写一条可被测试的使用条件和一条禁用条件；如果两支工具的边界讲不清，先合并或重新命名。
