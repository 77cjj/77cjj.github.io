做 Agent 前，先问一句：真的需要 Agent 吗？.

把单次调用、固定工作流与自主循环放在同一条复杂度轴上。

Dream · 2026.09短篇阅读札记
参考原文Anthropic · Building effective agents ↗以下是独立中文札记，并非原文翻译。来源观点与个人推论分开展示。

问题从哪里来

如果一个任务只要检索一次资料、生成一段答案，就能稳定完成，给它加规划器、记忆和多 Agent 协作，通常不是进步。Anthropic 把固定代码路径的 workflow 和由模型动态决定步骤的 agent 分开讨论，并建议从最简单、可测的方案开始。

原文给出的线索

  1. 固定的任务拆分适合 prompt chaining、路由或并行工作流；只有下一步难以预先写死时，自主 Agent 才更有价值。
  2. Agent 的成本不只是推理费用：更多轮次会带来延迟，也会让错误累积。终止条件和环境反馈必须写进设计。
  3. 框架可以缩短起步时间，但抽象层也可能挡住提示词、工具结果和失败原因。

我的理解 · 可以怎么试

我的判断是，先做一个单次调用基线，再逐个加检索、工具和循环。每增加一层复杂度，都用同一组任务比较成功率、耗时与成本；没有改善，就撤回。
